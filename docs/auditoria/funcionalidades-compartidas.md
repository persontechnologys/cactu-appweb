# Funcionalidades compartidas: Web / API / React Native

> Auditoría cruzada Fase 0.1. Objetivo: identificar dónde una misma regla de negocio existe en más de un lugar (`CLAUDE.md` sección 11, "una regla de negocio debe existir una sola vez"). No se corrige ninguna duplicación aquí — solo se documenta.

## Clasificación de la duplicación encontrada

- **Backend duplicado (Web vs. API, dentro de Laravel):** construcción de `detalle` (HTML) para los 5 tipos de carta — ya señalado en `problemas-detectados.md` antes de esta auditoría cruzada; esta auditoría solo confirma que el consumidor real de la ruta API es efectivamente el móvil (no queda como hipótesis). **Resuelto 2026-08-08** (ARQ-001, Fase 4) — ver `docs/cambios/decisiones-arquitectura.md`.
- **Backend/Móvil duplicado (regla de validación):** la lista de campos obligatorios por tipo de carta existe tanto en el `FormRequest` compartido por Web y API (`app/Http/Requests/Cartas/`, unificado 2026-08-08) como en cada pantalla de `CactuApp` (`validar()`). Importante — **no se debe considerar la validación visual del móvil como equivalente a la regla de negocio backend** (`CLAUDE.md` sección 20 y consigna de esta tarea): si un desarrollador móvil relaja `validar()` sin coordinar con el backend, el backend seguirá rechazando con `422` los campos que declara `required`; si un desarrollador backend agrega un campo `required` nuevo al `FormRequest` sin avisar al móvil, el usuario verá un error genérico sin que la UI lo prevenga antes de enviar. Esta pierna móvil es la única que queda pendiente de la triplicación original — no es una duplicación que se pueda eliminar sin compartir runtime entre PHP y React Native.
- **Web/Móvil duplicado:** la bifurcación "presentación mayor vs. menor según edad" (`edad > 5`) está implementada de forma independiente en el flujo web (`cartas-ninio.*`, no auditado en detalle en este documento por estar fuera del alcance de "React Native", pero mencionado en `integracion-movil.md`) y en `Presentacion.js` del móvil. No se confirmó si ambos usan el mismo umbral (`5` años) — **pendiente de confirmar** contra la vista Blade equivalente antes de tocar cualquiera de los dos lados.
- **Sin duplicación real:** autenticación, CRUD administrativo, descarga de PDF (mismo endpoint físico) y notificación push saliente — cada uno tiene una única implementación real, aunque consumida desde múltiples canales.

## Relación con el roadmap existente

Todo lo aquí encontrado refuerza, sin contradecir, lo ya priorizado en `docs/fases/roadmap.md` Fase 4 ("Unificación Web/API" — extraer Actions únicas para cada tipo de respuesta de carta, ARQ-001). Esta auditoría no agrega una fase nueva; confirma con evidencia del lado móvil que esa fase sigue siendo necesaria y de qué tamaño es (3 lugares distintos por cada uno de los 5 tipos de carta = hasta 15 puntos de mantenimiento manual para un solo cambio de regla de negocio).
